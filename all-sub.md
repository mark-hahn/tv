# Subtitles: how everything works

This document describes every piece of subtitle logic in the workspace as of 2026-10-11: where subtitle files come from, how they are named and cleaned, how their timing is checked against the video, how one is chosen when a video plays, how the players show them and let you switch or retime them, and how they are cleaned up. It covers tv-srvr, asr, tv-down, tv-api, tvapp, the phone remote, the web tv pane, and the browser players.

An `.asr.srt` has the video's timing but ASR's wording; the other files have a real subtitle's wording but often another release's timing. So a video whose only checked file is its `.asr.srt` gets one other file shifted by one offset to fit the `.asr.srt`, whenever one fits: the retime, built on 2026-10-11 ("Retiming against the `.asr.srt`"), backfilled the same day ("Backfill").

## The one rule

Every subtitle that is ever shown is a sidecar `.srt` file sitting beside its video in the same season folder. Subtitle tracks embedded inside a video are never shown and never served to a player. When the video lands on disk, its English or untagged text tracks are copied out to sidecars. Bitmap tracks (PGS and the like), forced tracks and tracks in other languages are simply ignored. Every subtitle file written anywhere, for any reason, goes through `cleanSrt()` in `packages/share/src/srt.js` first; tv-down, which copies an arriving `.srt` over from the seedbox, cleans it as soon as it lands. Movies get no subtitle processing, except what is asked for by hand from the local pane's EmbSub and ASR panes.

## Cleaning a subtitle file

`cleanSrt()` takes the raw text of a subtitle file and returns the cleaned text. When nothing needed fixing it returns the text exactly as it came. Cleaning first strips formatting: anything in curly braces (ASS override codes), anything in angle brackets (HTML-style tags such as italics and font colors), the ASS hard space, which becomes a plain space, and the ASS line-break codes, which become real newlines. It then parses the file into cues, keeping only blocks that have a time line and some text, and accepting either a comma or a period before the milliseconds. It sorts the cues by start time, because extraction from embedded tracks can produce them out of order, and merges cues that have exactly the same start and end into one cue whose lines are stacked.

The last step undoes "rolling" subtitles, a format that blinks on screen. Back-to-back cues with identical text and less than 250 ms between them are merged into one. If at least three of the remaining cues, and more than 15 percent of them, are shorter than 250 ms, the file is treated as rolling. Every such short cue that shares a line of text with the cue just before or just after it (within 500 ms) is then dropped, since it is only a transition between two real cues. If formatting was stripped, cues were reordered or merged, or rolling cues were dropped, the cues are renumbered from 1 and written back out in standard SRT form, with a comma before the milliseconds. Otherwise the text comes back exactly as it was, even when the parser had to skip a broken block or accept a period before the milliseconds.

## Names and types

A sidecar belongs to a video when its name is the video's name without its extension, followed either directly by `.srt` or by a dot, a suffix and `.srt`. The suffix is whatever sits between the video's stem and `.srt`, and it decides the sidecar's type (`sidecarType()` in `apps/srvr/src/subOrigin.js`).

There are five types. A suffix of T followed by a number is a copy of the video's own embedded text track with that stream index, type T. The legacy name `mb` followed by a number also counts as T. H followed by a number is the same kind of copy, but of a track flagged as describing music and sound (SDH), type H. `opn` followed by five or more characters is an OpenSubtitles download, type V; the characters are the OpenSubtitles file id written in base32 using the letters A to Z and the digits 2 to 7, padded on the left with A to five (an id of 32⁵, 33,554,432, or more takes six). The suffix `asr` is a transcript made by speech recognition, type "+". Anything else is type S: S followed by a number is a subtitle file that arrived beside the video and was renamed by tv-srvr. A bare `<stem>.srt`, or something like `<stem>.en.srt`, also counts as S.

Each sidecar also gets a short label for the subtitle panels (`sidecarLabel()`). It is the type letter and the number, such as "T 3", "H 4" or "S 1". A download shows as V and its tag, such as "V CYR4Q", and an ASR file shows as a lone "+". An S file with an odd suffix shows as S followed by that suffix, and a bare `<stem>.srt` as a lone "S".

`listSidecars()` in `apps/srvr/src/subs.js` lists a video's sidecars in a fixed order: T first, then H, V, S and finally +. Within a type the files are in natural filename order. A play's list (`playList()`, described under "Which subtitle a video starts on") is this list with the misfits left out and the rest grouped by their checks, each group keeping this order, and the order is also the fallback preference when nothing else decides which subtitle to start on. Only lower-case `.srt` names count, so the watcher renames a `.SRT` file that arrives to `.srt` (leaving it as it is, with a log line, when that name is taken), and tv-down lands one as `.srt`.

Sidecars that tv-srvr names itself (T, H, `mb`, S with a number, `opn` and `asr`) are recognised by `NAMED_SIDECAR_RE` in `apps/srvr/src/subsQueue.js`, which, like `sidecarType()`, minds case except in an `opn` tag, so a name such as `x.t3.srt` counts as arrived and is named. Any other `.srt` that appears in a show folder is treated as a newly arrived file that still needs naming.

## The subtitle database

`apps/srvr/data/subs.db` is a SQLite database owned by `apps/srvr/src/subs.js`, and tv-srvr is its only writer. It has six tables.

The subs table holds every result an OpenSubtitles search has ever returned for an episode. Each row is keyed by show id (the TVDB id), season, episode and OpenSubtitles file id. Rows keep the order in which the searches first returned them. Each row records the result's flags (hearing impaired, hd, foreign parts only, AI translated, machine translated), its frame rate, uploader id, upload date, release name, comments and episode title. It also carries two markers: downloaded, which follows the disk, and chosen, set on the download that was showing when the episode was last stopped. A row is downloaded only while its `opn` file sits beside one of the episode's videos that is not a sample (`syncDownloaded()`); the mark is set again on every `.srt` add or delete the watcher sees and on every search, and the 6-hourly sweep clears it for episodes left with no video, but only after a walk that read every folder and found videos, so a disk outage clears nothing. Two more columns hold a video path each: unfitFor, the latest video the file was found not to fit (set on every row with that file id), and hashFor, the video OpenSubtitles says the file was made for, by the video's hash.

The picks table holds, for each episode, the sidecar that was showing at its last real stop: its suffix, its type and a timestamp. The processed table holds the paths of videos that have been through the add-to-disk steps described below.

The other three hold what the timing checks described below learn. The clips table holds, for each checked video, the words heard in its clips with their times, the clip positions, the middle clip when one was taken to test the file's rate, and the audio track they came from, or track -1 (with no clips) for a video with no English audio. The checks table holds each sidecar's verdict, offset, the method that found it and a note, together with the file's size and modification time and its video's path; a verdict counts only while the file still has both, and the video's path lets a deleted video's checks go with it. The asrSpend table holds, for each day, Los Angeles time, the estimated cost of the automatic complete ASR runs queued that day, at 38 cents an hour of the video's length, added when a run is queued whether or not it then succeeds. Speechmatics' real usage is recorded separately, in `apps/srvr/data/asrjobs.db`.

one more table. The retimes table holds, for each video, when its retime pass last ran and the file it retimed, or none. It keeps the queue from repeating a pass that found nothing.

## When a video lands on disk

tv-srvr watches `/mnt/media/tv` with chokidar. It ignores dot files and waits until a file has stopped growing for two seconds. When a video file appears, the show's disk cache is updated, and the new files for that show are gathered until three seconds have passed with no new one. They are then handled only if the show has a TVDB record and is in the library. With no record, a log line notes that the files skipped the subtitle queue. A show not in the library is skipped silently, and since the library sweep that takes a new folder into the library runs after this check, the videos of a brand-new show wait for the 6-hourly sweep described below.

The watcher does not report the files already there when it starts, so a file that lands while tv-srvr restarts, most often a download that finishes during a deploy, would raise no add. Once the watcher's first walk is done, every video and `.srt` whose change time is no more than a minute before the process started gets the add it missed (`replayMissedAdds()` in `index.js`). Anything that landed earlier, during a longer downtime, waits for the sweep. A video deleted from the show while its new files are being gathered does not cancel them; the show is refreshed once they are handled.

A video rewritten in place under the same name, as a forced tv-down download is (rsync fetches over the existing file) or as tv-down's remux of an mkv for tvapp seeking is, raises a change event. It is treated as another file (`videoReplaced()` in `index.js`): one the TV player stalls on goes to the recode queue, and any other goes on the sub queue with the naming instruction and a mark that it was replaced. That entry first forgets everything learned about the old file (its clips, its checks and its processed row) and deletes the T and H copies of the old file's tracks, then takes the steps below; the video's other sidecars stay and are judged against the new file like any others.

Each new video first goes through two checks. If another video of the same episode is already present, and both resolutions are known and differ, the lower-resolution one is deleted together with its sidecars, and if the new file is the loser it is not queued. The resolution is read from the file name, and only 2160p and 1080p count as known, so a 720p copy beside a 1080p one is left alone; with three or more copies every one below the best is deleted. If the video is one the TV player stalls on (an `.avi` or `.divx` file whose codec tag is DX50, DIV3, DIV4, DIVX, MP43 or MP42), it goes to the recode queue instead. The recode writes an h264 mkv with the same stem, keeping only the first video and audio streams and discarding embedded subtitle streams, and moves the original to `/mnt/media/tv-recode-originals`, where it is kept 30 days. The output then arrives as a fresh add and takes the normal path; sidecars already beside the original stay, since the new file is the same cut. Every other new video is put on the sub queue with the instruction to name any arrived subtitle files.

The sub queue is a list of entries persisted to `apps/asr/data/subQueue.json`. Queuing a video already in the list never adds it twice. A second request merges into the first: a request to name arrived files carries over, and a normal-priority request moves a low-priority entry to the front, while an entry already at normal priority stays where it is. A request for the video whose entry is running at that moment is held, merged with any other such request, and queued again once the run is done, so a subtitle file that arrives, or the video changing, mid-run is not lost. Requests through `/api/asr/subs/enqueue`, which the web client's local pane uses, go to the front; with `lowPriority` set, used by backfill scripts, they go to the back at low priority, as the sweep's do. an entry can also carry the retime mark (`retime` on `/api/asr/subs/enqueue`, set by the watcher when an `.asr.srt` lands and by the backfill), which makes it run the retime pass alone, without the steps above; merging two requests keeps the mark. A loop checks the queue every 10 seconds when it is empty and every half second while it has work, and every request wakes it at once. Entries are processed strictly one at a time. An entry stays in the queue while it runs and is removed when it finishes, even if it fails; if tv-srvr is killed in the middle, the entry is still in the file and runs again after a restart. Every step skips work that is already done, so running an entry twice is harmless.

Processing one entry goes like this. If the video file is gone (most often because it lost to a higher-resolution copy and was deleted), the entry is dropped. If it is under `/mnt/media/movies`, it is dropped with a log line, because movies get no subtitle processing. Otherwise the season and episode are parsed from the file's path and the show's record is looked up. Season 0 specials go through every step below like any other episode, and OpenSubtitles is searched with season 0 for them.

The first step copies out the embedded text tracks. ffprobe lists the video's streams. If ffprobe fails, the entry ends with an error and is not marked processed, because treating a failed probe as "no embedded subtitles" would send a video with perfectly good tracks off to paid ASR; the sweep will bring it back later. A stream is copied out when it is a subtitle stream in a text format (subrip, ass, ssa, webvtt, mov_text, text or srt), its language tag is `eng`, `en` or missing (not `und`), and it is not flagged as forced. Each such stream becomes `<base>.T<n>.srt`, or `<base>.H<n>.srt` when it is flagged as hearing impaired or its title contains "SDH", where n is the stream index. Nothing is written when that file, or the legacy `<base>.mb<n>.srt`, already exists. ffmpeg converts the stream to SRT, running in the idle CPU and idle disk class, through a small serial queue shared by every extraction so a whole season can't start a crowd of ffmpegs at once. The result is written through `cleanSrt()`, and only when the output contains at least one time line; a failed conversion writes nothing and does not end the entry.

The second step, for videos that parse to a season and episode and whose entry carries the naming instruction (the watcher's do; the sweep's and the local pane's don't), gives arrived subtitle files their names. It looks at every non-hidden `.srt` in the folder that is not already a named sidecar and not another video's own file, and that parses to the same season and episode. Each is cleaned and added as the video's next S file, numbered one past the highest S number there. If an existing S file already has exactly the same text, the new one is a duplicate and is not added. Either way, the original file is deleted.

The third step checks the timing of every subtitle file beside the video, as described in the next section, and downloads from OpenSubtitles when none fits. If a check, search or download fails, or the video's checks are already running for a remote's Sync, the entry ends without being marked processed and without going to ASR, with a log line naming the stage it failed at, and the sweep brings it back.

The last step decides about ASR. The video goes on the ASR queue when the checks left it with nothing that fits and it has an English audio track. ASR started this way may cost at most $20 a day, Los Angeles time (`AUTO_ASR_DAILY_USD` in `subsQueue.js`). The cost is estimated at Speechmatics' 38 cents an hour of the video's length and booked when the video is queued, and it is not given back if the ASR then fails or is aborted. A video that would go past the limit is not queued and not marked processed, with a log line, so a later sweep brings it back on another day. ASR that follows the local pane's Subs, or that is asked for from the ASR pane, is not counted or limited. Finally the video is marked processed.

a retime step comes between the checks and the ASR decision. When the checks leave the video with an `.asr.srt` and no other good file, the entry runs the retime pass described under "Retiming against the `.asr.srt`", unless the video has a retimes row already. A video only now going to ASR has no `.asr.srt` yet; it gets its pass when the ASR file lands (see ASR).

## Checking the timing

`apps/srvr/src/subPrepare.js` decides what is done with each subtitle file, out of pieces in `apps/srvr/src/subSpotCheck.js`, and `srt-fix.md` explains why it works this way. The reference is the words spoken in the video's own English audio track, the first one tagged `eng` or `en`, else the first track when it is untagged or tagged `und`. Two two-minute clips of that track are cut at idle priority and transcribed by Speechmatics at once, which takes about ten seconds and costs about 2.5 cents. They sit at the stretch with the most dialogue cues (cues with words left once tags, bracketed sound notes, ♪ and punctuation are taken out) in the first third and in the last third, by cue count, of the first usable sidecar in type order. A clip that gives no file at least ten pairs, because it fell on music or a scene in another language, is cut once more at the next busiest stretch of its third that is at least two minutes from every stretch already tried; with none, the first clip stands. Each extra clip is another Speechmatics job of about 1.3 cents. The clips are stored in subs.db, so every later check of any file of that video is a comparison that costs nothing.

The clip jobs (`transcribe()` in `subSpotCheck.js`) send 16 kHz mono FLAC, in English, at the "enhanced" operating point, and poll every second, giving up after 300 polls. A request whose connection drops with no answer is sent once more after two seconds (`smFetch()`), since a job already submitted is paid for; an error answer is not retried.

Before any of that, a file with fewer than three dialogue cues a minute of video is a signs or forced track, and a file with less than 0.18 of its words among a list of common English words is not English. Both are unusable.

For each clip, a cue within a minute of it pairs with the clip's words when its first five words (all of them, for a shorter cue) appear exactly once among the cues near the clip and exactly once in the clip. The difference between the word's start and the cue's start is that pair's offset, and the median of the pairs is the clip's offset; it is positive when the captions come before the words. A clip is solid for a file when it has at least ten pairs and its median is pinned to within 80 ms, measured as the median distance of the pairs from it over the square root of their number.

When both clips are solid and agree within 250 ms, their mean is the file's offset. The file is good when that offset is from 250 ms late to 500 ms early, and fixable otherwise. When both are solid but disagree, a third clip is taken at the busiest stretch of the middle third of the file's cues that overlaps neither of the other two, and is stored with them. If it is solid and its offset lies within 250 ms of the line through the other two, the file runs at another rate and is fixable by moving every cue by the offset on that line, which stretches or shrinks it. Otherwise, or when there is no room for a middle clip, it is from another cut. When a clip is not solid, the file can't be told. A file whose cues run past the end of the video is judged like any other: one from another cut is found by its clips, and one at another rate is stretched to fit. Only when such a file can't be told, and its last cue ends more than five seconds past the end, is it taken to be from another cut.

A good file is kept. A fixable file is shifted or stretched through `cleanSrt()` and judged again from the stored clips; the five-second rule is not applied to it. A file that is unusable or from another cut, after a fix or not, is deleted: a subtitle file the checks have found useless has nothing left to offer, and what was found is kept in its check row as the memory of why. That memory stops the queue from copying the same track out of the video again, and the watcher keeps it when the file goes, where it forgets any other deleted file's check. An OpenSubtitles file's result is also marked unfit for the video, so it is never downloaded for it again. The one exception is an unusable `.asr.srt` (a transcript of a video with no English dialogue, or with too little), which stays, since ASR never runs for a video that already has one; an `.asr.srt` from another cut, mostly a copy inherited from a replaced release, is deleted like the rest. A file that can't be told is kept. Until 2026-10-12 only OpenSubtitles files were deleted and the other misfits stayed on disk unoffered; `apps/srvr/scripts/delete-misfit-subs.js` deleted the ones left.

beside a video that has an `.asr.srt`, a file that is not good (from another cut, can't be told, or still fixable after its fix) is first retimed against the `.asr.srt`. Only when that fails is it dealt with as above.

When nothing is good after that, and the video is an episode of a show with an IMDb id, OpenSubtitles is searched and candidates are downloaded one at a time, best first by the order described under OpenSubtitles, each judged as it lands and dealt with in the same way. It stops at the first good one, after five tries (a download that fails counts as one), or when no candidate is left. When the video has no stored clips yet, because it had no usable subtitle file, the first download places the clips, and takes a middle clip when it needs one. With still nothing good, the video needs a complete ASR, which fits it by construction.

A good `.asr.srt` counts as a fit like any other good file, so a video that has one gets no downloads here. That is still so, but when it is the only good file, the retime pass that follows tries the other files on disk, and downloads when none fits.

A video with no English audio track has no words to match; its clips row is stored with track -1 and no clips. Its T and H files are presumed good, since they came out of the video: they count as a fit, so no download or ASR follows, but they are stored as "can't tell" with the note "presumed good", so a play offers them without a ✓, after any checked good file. Every other file is checked by whole-file audio matching (`syncSubToAudio()` in `subSync.js`), where ffsubsync lines the cues up with the speech its voice detector hears in the first audio track, looking up to a minute either way; it passes a file only when the whole file's offset and the best offsets of its first and last thirds agree within 250 ms, and shifts it by that offset. A file it can't pass is stored as "can't tell" and kept, a download included, so with no T or H file up to five downloads can be left beside the video. Such a video never goes to ASR.

When a sidecar appears later beside a video with stored clips, whether a download at play, an arriving file or anything else, the watcher judges it from the stored clips and deals with it in the same way (`subFileEvent()`), unless it already has a verdict for the file as it is. When the video's checks, or another file's judging, are running, it waits until they are done, so files that land together are all judged. When the file's two clips disagree and the video has no middle clip stored, the watcher hears one and stores it, as the video's own checks do, so a download that only runs at another rate is stretched rather than deleted. For a video with no English audio the watcher runs the whole-file audio matching again, which can take minutes. When a sidecar changes by anything other than these checks, most often by a panel's Apply, its timing was set by hand, and it is judged again from the stored clips without being shifted (`judgeHandTimed()`). It keeps a verdict, and its ✓, only when it now fits; otherwise it is unchecked and is offered without a ✓, after the checked files. On a video with no English audio a file timed by hand always loses its verdict. Nothing checks an unchecked file again by itself while `SUB_CHECK_BACKFILL` is off; with it on, the sweep queues the episode. Any run of the queue's checks, the local pane's Subs included, judges every sidecar afresh and may shift a file timed by hand to the timing it measures. A deleted file loses its verdict, unless it was a misfit, whose verdict is kept as said above; a deleted video loses its checks and clips, and its processed row and the unfit marks naming it stay. A video counts as checked when it has stored clips and every sidecar beside it has a verdict for the file as it is now, other than fixable, by its path, so a replacement or a renamed file is checked again, and so is a video whose clips came from a dry run or a remote's Sync.

when a sidecar arrives beside a video that has an `.asr.srt` and no other good file, and the clips do not find it good, the watcher retimes it against the `.asr.srt` there and then; downloads are left to the queue's pass. When an `.asr.srt` lands from an ASR job, the watcher queues the video with the retime mark. Anger Management S02E88 shows the need. Its `.asr.srt` was found good on 2026-10-08. A play on 10-10 downloaded two HDTV files: one was deleted as another cut, and the other, `opnCTAPH`, was never judged, because the watcher then dropped a file that landed while it was busy (it now waits). It was offered unchecked, with HDTV timing, beside "+ ✓", and nothing as built would ever have fitted it.

## Retiming against the `.asr.srt`

The goal: a video whose only good subtitle file is its `.asr.srt` gets one other file shifted to fit it, so at least one file has both the right wording and the right timing.

A video needs a retime when it has an `.asr.srt` and no other sidecar checked good.

The retime is the local pane's Sync (`syncSubToAsr()` in `subSync.js`), run by itself. It takes the file's phrases of one to four words, sound notes left out, that occur exactly once in both the file and the `.asr.srt`; the median of their start-time differences is the offset. It needs at least ten matches. One rule is added: at least 80% of the matches must lie within 250 ms of the median, or the file is from another cut and no one offset fits it. The file is shifted by the offset, never below 0, through `cleanSrt()`, under its own name, and its verdict is stored as good, method "retime", with the offset and the match count, so a play offers it with a ✓. A file that can't be retimed is left as it was.

Which files: every sidecar on disk other than the `.asr.srt` that is not checked good and not unusable, T and H first, then V, then S, each tried in turn until one fits. When none fits, the pass downloads from OpenSubtitles, candidates in the usual order, retiming each as it lands, until one fits, five have been tried, or no candidate is left. A download that doesn't fit is deleted and marked unfit, as now.

The pass ends by writing the video's retimes row, and logs one line with the show, the episode, the file and its offset, or that nothing fitted.

It runs in four places: in a sub queue entry after the checks; alone, from an entry with the retime mark (an `.asr.srt` landing, the backfill); from the watcher, for a sidecar arriving beside a video that needs one; and from the local pane's Sync, for the selected file. Only the first two download.

### What the retime changed

- "The subtitle database": the retimes table.
- "When a video lands on disk": the retime step after the checks, and the retime mark.
- "Checking the timing": a file not good beside an `.asr.srt` is retimed before it is deleted or hidden; the watcher retimes arrivals and queues a pass when an `.asr.srt` lands.
- "ASR": a landing `.asr.srt` queues the pass.
- "Which subtitle a video starts on": a good `+` file is chosen only when no good file of another type is there.
- "Web client panes": Sync gains the 80% rule.
- "Backfill plan": new.

Nothing changed in the clip checks, Speechmatics use, the players, the remotes' panel, or the `.asr.srt` files.

## Subtitle files that arrive on their own

When the watcher sees a new `.srt` that is not a named sidecar, in the folder of a library show, it parses the season and episode from the file name (using the folder name as a hint). It then looks for the first video of that episode in the same folder. If one is there, that video goes on the sub queue with the naming instruction, and the second step above turns the file into an S file. If the video is not there yet, nothing happens now; when the video arrives, its own trip through the queue picks the file up. If the video's entry is running at that very moment, the video runs again once that run is done, and the file is named then.

tv-down brings `.srt` files over from the usb seedbox. It takes one only when its episode's video is already on disk (a video in the season folder whose name holds the zero-padded SxxEyy), is being downloaded, or is queued for automatic download in the same cycle. A video from the torrent pane, a forced download or a special does not count as queued in the same cycle, so its `.srt` comes over on the next one. tv-down also skips an `.srt` whose episode is watched, whose show is not in the library, or that is already at its destination or already in tv.json. It puts the file in the show's season folder under its original name, with two exceptions. An NNN or NxN episode number at the start of the name, or NNN inside it, becomes `SxxEyy - <rest of the name>.srt`; for example `1x1 - The Sofa.srt` becomes `S01E01 - The Sofa.srt`. A name that still has no two-digit SxxEyy marker becomes `<show folder> SxxEyy.srt`, and a `.SRT` extension becomes `.srt`. A release's own subtitles often sit in `Subs/<episode folder>/<n>_<lang>.srt`, where only the folder names the episode and every episode's file has the same name. tv-down takes the English ones (a name holding "eng" or "english" as a word, such as `2_eng.srt` or `2_eng,English.srt`): it knows such a file as `<episode folder>/<name>`, which is unique where the name alone is not, parses the show and episode from the folder, and lands it as `<episode folder>.<name>`, which is a sidecar of the video named like the folder. The other languages in that layout have no episode and are skipped like any such file. Once a file has landed, tv-down rewrites it through `cleanSrt()`; naming it is left to tv-srvr. An arriving `.srt` never makes tv-down delete anything, and it is exempt from the video quality and duplicate rules. A forced download skips the video check and the other skips entirely. An `.srt` whose name and top folder give no season and episode, or no title, is skipped with a log line, never an error entry. Such files usually share names like `5_spa.srt`, so one error entry would block all the others. Each skip is logged once per usb path; the paths are kept in tv.sqlite's `skip_logged` table, so a restart does not log them again, and dropped once the file has left the usb. Movie downloads copy video files only, never subtitles.

## The backstop sweep

The watcher is the only normal path into the sub queue, and it once silently lost every download for shows whose folder name differs from their TVDB name. So a second path walks the whole library: 10 minutes after tv-srvr starts and then every 6 hours. It reads each show folder's season folders, so a video lying directly in a show folder is never swept. It queues, at low priority, every video of a library show that is not already in the sub or ASR queue, and has not been processed, watched or not, whatever subtitle files it already has. Its entries carry no naming instruction. The same walk sets every episode's downloaded marks, as described under the subtitle database. Its entries come after all other batch work: while a stills build (an intro strip or a play set), a recode or ASR is running or queued, the sub queue takes only entries from the watcher or the local pane. An entry already running when such work starts carries on to its end. This is also how videos that were on disk before the queue existed get their embedded tracks copied out, including the ones that already had downloaded or ASR files. A settled library adds nothing, so the sweep is just a directory walk. When `SUB_CHECK_BACKFILL` in `index.js` is turned on, which it is not yet, the sweep also queues every library video that does not count as checked (`needsCheck()`), mostly ones processed before the timing checks existed.

## ASR

The ASR queue is persisted to `apps/asr/data/asrQueue.json`, and a video is never in it twice. Videos reach it from the sub queue's last step, from the web client's ASR pane, or through the ASR enqueue endpoint. A loop runs one job at a time: it checks every 10 seconds when the queue is empty and every half second while it is working. A job whose video is gone, or that already has an `.asr.srt`, is skipped with a log line.

A job runs `apps/asr/asr.js` as a child process in the idle CPU and idle disk class. It passes the video's path and a vocabulary list built from the show's TVDB character names: each full name (a character field holding several is split at its slashes), with the titles Dr, Nurse, Lt, Mr, Mrs and Ms removed, plus every word of it longer than two letters. asr.js extracts the video's first audio track as mono 16 kHz FLAC and uploads it to Speechmatics as a batch job, in English, with the "enhanced" operating point and the names as additional vocabulary. It polls every 5 seconds, giving up after 240 polls. Failed requests and HTTP 429, 500, 502 and 503 answers are retried up to five times, with waits that double from 5 seconds. The json-v2 transcript gives every word its measured start and end, and punctuation is glued onto the word before it.

Cues are built from those word timings. A new cue starts at a gap in the speech longer than one second, when the next word would push the text past 84 characters, or after a sentence end once the cue holds at least 28 characters. A cue's words are grouped again by the same 84 and 28 character rules, which rarely splits anything further, and each piece gets the real times of its own words. Each cue longer than 42 characters is wrapped onto two lines of at most 42, breaking preferably after a sentence end, then after a clause end, and otherwise where the two lines come out most even. When no break keeps both lines within 42, the most even break is taken anyway, so a line can run longer.

The timings are then made readable. A cue's reading time is its length at 16 characters a second, kept between 0.35 and 12 seconds. A cue that would stay up longer than two and a half times its reading time plus a second is cut back to 1.6 times its reading time plus 0.4 seconds. Cues that start less than 0.45 seconds apart are merged when the joined text fits. After that, every cue starts at least 0.98 seconds after the one before it. Each cue is held for at least 0.9 seconds and never less than 0.35, and it ends 80 ms before the next one starts. Stretches of 30 seconds or more with no speech are reported in the log. The result is written through `cleanSrt()` as `<stem>.asr.srt`, and the temporary audio file is deleted.

when the `.asr.srt` lands, the watcher queues the video with the retime mark, so one other file is fitted to it (see "Retiming against the `.asr.srt`").

Everything the job prints goes to a buffer shown in the ASR pane, to `apps/asr/data/subtitle.log`, and to the web client. The log is rotated daily at 5 am Los Angeles time into `subtitle-logs/subtitle-MM-DD.log`, named for the day that ended. The Queues pane's stage text ("starting", "extracting audio", "uploading audio", "transcribing", "transcribing, retrying", "writing subtitles") is read off those printed lines, and its ETA is a flat 60 seconds per job. A job can be aborted with the ASR pane's Abort, which sends SIGTERM to asr.js; asr.js then kills its own ffmpeg and exits, and the log records the job as cancelled. Removing the running entry from the queue kills it the same way, but the log records it as an error exit, not as cancelled. While the ASR queue is not empty, the client header shows "Asr:" and the queue's length.

## OpenSubtitles

tv-srvr talks to the OpenSubtitles REST API in `apps/srvr/src/opensubtitles.js`, using the API key, username and password in its secrets folder and a fixed "tv-srvr v1.0.0" user agent, because the API rejects generic ones. The login token is cached in the secrets folder. At startup it is renewed when it is missing, expired, or within a day of expiring. A search answered with 401 or 403 logs in again and retries once. A search asks for English subtitles for the show's IMDb id, season and episode, and only the first page of results is used. It also sends the video's OpenSubtitles hash, made from its size and its first and last 64 KB, which does not narrow the results but flags those made for that file. A download first asks the API for a link to the file and then fetches it. The link request is tried up to three times on 502, 503 and 504 answers or network errors, waiting a little longer each time. A 429 answer, the API's limit of five requests a second, is retried after the one second its retry-after header asks for.

Downloads happen in three places: in the timing checks, one at a time as described above; just before a video plays (`subsBeforePlay()` in `subs.js`), which is the same for tvapp and the browser player; and ahead of a play (`prefetchSubs()`). If the episode already has three downloaded files, or a file other than its `.asr.srt` checked good (`hasGoodSub()`), nothing happens. If the show has no IMDb id, nothing happens beyond a log line. Otherwise a fetch job starts, unless one is already running for that episode, in which case that job is shared, so a play can find itself waiting on a prefetch. The job searches again, storing any new results. It then downloads all the candidates the episode still needs at once, and replacements for any that failed, until the episode has three downloads, three downloads have failed, or no candidate is left. A failed search ends the job with nothing downloaded; it does not fall back on stored results. Only searches log in again on a 401 or 403, downloads do not.

The prefetch fetches an episode's downloads before anyone plays it, and nothing waits on it (`prefetchNextSubs()` in `index.js`). It runs in two cases. After a play's own downloads have finished, or at once when there were none to wait for, it fetches the next unwatched episode with a file after the one playing, in story order (specials included), so the two never share the API's five requests a second. And whenever tv-srvr refreshes a library show that was played in the last 30 days (`PREFETCH_PLAYED_MS`), it fetches the show's next-up episode.

The candidate is chosen among the not-yet-downloaded results that are not marked unfit for the video, in the order the searches returned them. It is the first made for the video by its hash, else the first from the video's release group (the end of its name after the last dash), else the first from the same origin as any file chosen for any episode of the show, else the first that is not foreign-parts-only. Each download is written through `cleanSrt()` as `<stem>.opn<TAG>.srt` and marked downloaded, and the watcher has it judged when the video has been checked.

The play waits for the job for at most 5 seconds. If the job takes longer, the video plays anyway and the job carries on in the background. When it finishes, tv-srvr sends every client a `subsLate` message with the episode's new play list and pick. tvapp takes it only when the same episode is still up and opened with no subtitle file at all: it then reopens the video where it is, keeping the frame on screen, with the new list, starting on tv-srvr's pick. A video that opened with some subtitles keeps its list, and the browser player ignores the message, so for them the new files are there the next time.

tv-srvr sends a `subError` message to every client when the wait ran out, when a search or download failed, or when the video has no subtitle file at all once the wait is over, which also covers a show with no IMDb id. All of these go into one message. The "no subtitles" test counts every sidecar on disk, so a video whose only files are from another cut or unusable plays with none offered and no pop-up. The phone shows it as a pink pop-up box over a dimmed screen, and the web client shows the same box over every pane, though under its in-app video overlay. The text names the show and episode and says that the download took more than 5 seconds, what failed, or "no subtitles", separated by semicolons. The pop-up stays until its Close button is pressed, and a newer error replaces the text. On the phone it sits above every screen, the subtitle panel and the other full-screen views included.

## Same origin

Two OpenSubtitles results for different episodes of a show are said to come from the same origin when a choice made on one should carry over to the other (`sameOrigin()` in `subOrigin.js`). Their five flags must match: hearing impaired, hd, foreign parts only, AI translated and machine translated. Their frame rates must be equal unless either one is unknown (zero).

When both were uploaded by a real person, they must have the same uploader and upload dates within an hour of each other, since that is one person's batch. When either uploader is one of the shared bot accounts (os-auto 3282, os_robot 119465 and system 2), or has no uploader id, whose uploads are imports from everywhere and whose dates are import dates, the release names are compared instead. Each name is lower-cased, its punctuation is turned into spaces, and the episode marker (SxxEyy, NxNN, "episode N" or the bare season-and-episode number) and the episode's title are taken out. The two results match when what is left is equal and not empty, or else when their comments are equal and not empty. `apps/srvr/scripts/check-sub-origin.js` checks these rules against real search results.

## Which subtitle a video starts on

When tvapp or the browser player asks tv-srvr's `getPlayUrl` what to play, the reply lists the episode's sidecars in panel order (`playList()` in `subs.js`). Files checked good come first, with a ✓ after their label, then T and H files that were checked but could not be told (the presumed-good ones of a video with no English audio among them), then every other file: those never checked, and V, S and + files that can't be told or are still fixable after their fix. Files from another cut and unusable files are left out. Each entry carries a URL that serves the file as WebVTT, the panel label and the file name, together with `subPick`, the index of the one to start on, or -1 when nothing is offered, and `subsChecked`, whether the video's files have been checked. Embedded tracks are never in the list.

The start is `pickSidecar()`'s choice among the first of those groups that has any files, so a verified file is always preferred.

The first choice is the file this episode itself last showed, if that file is still on disk. Failing that, tv-srvr takes the type of the subtitle the show most recently showed in any episode. If that type is V, it looks for a downloaded file of this episode whose search result comes from the same origin as any chosen file of the show. Otherwise, or if no such file exists, it takes the first sidecar of that type. When the show has no history at all, or has none of that type here, the first sidecar in the list is used, so the order T, H, V, S, + is the default preference. Turning subtitles off is never remembered: a stop with subtitles off records nothing, so the next play starts with subtitles on again.

a good `+` file is the start only when no good file of another type is there. The episode's own last-shown file is passed over when it is the `+` file and a file of another type has been checked good since that stop. The show's last-shown type steers this episode only when it is not `+`, or when this episode has nothing else good. Once a retimed file exists, plays start on it. Picking `+` in the panel afterwards is still remembered for the episode, because that stop comes after the retimed file was checked.

## Which subtitle a video stopped on

Both tvapp and the browser player send the file name of the subtitle currently showing, or an empty string when subtitles are off, in every `playProgress` report. tv-srvr acts on it only at a stop: any `stopped` or `ended` report. A stop within the last four minutes counts as the end, which matters only for marking the episode watched. A `stopped` report in the first 10 seconds counts as never having played, and it chooses nothing; an `ended` one always counts, so tvapp's tap on Up, which ends the episode, records the subtitle even then. At a counted stop with a subtitle showing, that file becomes the episode's pick in the picks table, with its type and the current time, provided it is a sidecar of the episode's active video. If it is a download, its search result becomes the episode's only chosen row; if it is any other type, none of the episode's rows stay chosen. The pick decides where this episode starts next time, the type and timestamp steer the show's other episodes, and the chosen rows steer which downloads are tried first for the rest of the show.

## Serving subtitles to players

`/api/subtitle` takes a video path and a sidecar file name, and the path must be under the TV or movies folder. Only the name's base is used, and it must end in `.srt` (400 otherwise). It reads the `.srt`, changes the comma before the milliseconds to a period, puts a WEBVTT header on top, and returns it with `Cache-Control: no-cache`, so an edited file is always fetched fresh. It answers 404 when the video is gone, and when the file is gone, which happens when a check deletes a file a play offered moments before; any other failure is a 500. It serves the file exactly as it is on disk; a timing change exists only as an edit to the file itself. `/api/subtitle-list` lists every sidecar of a video with its label, for the web client's in-app player, with no checks applied: nothing is left out and nothing gets a ✓.

`/api/stream`, the browser's video stream, carries no subtitles at all.

## tvapp

tvapp's `VideoPlayer` (Media3 ExoPlayer) adds every sidecar from `getPlayUrl` as a side-loaded WebVTT subtitle with its panel label. The tracks get no language and no default or forced flags. When the tracks first become known, it turns on the one at `subPick`; if there is none, it turns the text track type off altogether. Because text is either forced onto a side-loaded track or switched off entirely, Media3 can never fall back to a track embedded in the file, and only the side-loaded tracks are ever offered for selection. tvapp sets no subtitle size, color, position or background, so they take Media3's player view default, which follows the TV's own caption settings. Trailers play with captions off.

When the downloads a play could not wait for land, tv-srvr's `subsLate` message reaches tvapp on its update socket, which is open only while tvapp is in front (`addSubs()`). tvapp takes it only when a video of that same show, season and episode is up and opened with no subtitle file. It then takes the new list and pick, and reopens the video where it is with the frame kept on screen, starting on tv-srvr's pick, as a reload does. The episode's `subsChecked` is not updated by it.

tvapp sends the remote the subtitle list as `l,` followed by JSON. The JSON holds a title made of the show name and the SxxEyy code, the tracks (each with its label and the type "srt"), the index of the selected track or -1, the timing offset described below, whether Sync is allowed, and the caption line: the captions the offset puts at the video's position. tvapp fetches the showing track's file for it, strips its tags, and looks up the captions at the position less the offset every 50 ms. The list goes out every time the player's tracks change, whenever the offset moves, whenever the caption line's text changes, when a Sync starts and ends, after an Apply lands, and whenever the remote asks with `l`. When a video closes, tvapp sends `l,null`; playing another episode closes the first, so a null list is sent before the new one. A `t,<n>` command turns on track n, and `t,-1` (or any number out of range) turns subtitles off. Choosing a different track resets the offset to zero.

While a scrub hold is on, the full-screen stills cover the video and its subtitles until the hold has landed. The camera overlay does not change the subtitles, and the subtitle commands (`l`, `t`, `so`, `sa`, `sy`) still work while it is up; `k,reload`, like every other key, is swallowed.

## The subtitle panel on the remotes

In tvapprc mode, holding Vol+ for 400 ms on the phone remote or in the web tv pane opens the subtitle panel; a shorter press is an ordinary volume step. Outside tvapprc mode, holding Vol+ just turns the volume up one step. In the phone's "linda" layout, holding Vol+ in tvapprc mode does nothing at all, not even a volume step, and the web pane does nothing at all while the TV is off.

Opening the panel sends `l`, and the panel shows the most recent list tvapp has pushed. Lists keep arriving whether the panel is open or not, and the panel always shows the newest. Its header is the video's title, or "No video playing" when the list is null. The body is a grid of buttons: "None" first, then one button per track showing its label, with the selected one shaded light blue and in bold. Tapping a track sends `t,<n>`, and tapping None sends `t,-1`. The tap marks the selection at once and the next list from tvapp confirms it. Tapping does not close the panel. Only its Close button does, and the panel stays open even when the video stops or tvapprc mode ends. A video that stops, or tvapp going to the background, sends `l,null`, so the panel then says "No video playing"; the last real list stays up only when the bridge drops some other way.

Between the grid and the offset is the caption line, four lines tall in bold black on white, showing the caption line tvapp sends.

Below that is the timing offset. It shows the offset in seconds, in tenths, or in hundredths when it is off them (as one Sync measured can be), beside an Apply button, and below it two rows of "-" and "+" buttons that move it by half a second and by a tenth of a second either way. Each move is sent to tvapp as `so,` and the number of seconds, and tvapp adds it to its offset and sends the list back. The offset counts from the file as it is on disk now. Nothing is shifted until Apply, which is enabled only when a track is selected and the offset is not zero. Apply sends `sa`. tvapp then asks tv-srvr's `/api/applySubOffset` to shift the selected sidecar on disk by the offset, in milliseconds. tv-srvr moves every cue's start and end by that amount, never below zero, and writes the file back through `cleanSrt()`. It refuses a video outside the TV folder, so a movie's files can't be shifted, and an offset of zero writes nothing. When the shift succeeds, and the same video is still up, tvapp takes the offset back to zero, keeping any move made while the request was out, and reloads the video at the same position, keeping the same track, so the edited file is fetched again. A failed Apply changes nothing and says nothing.

The shift is permanent and applies to everyone who plays that file afterwards. A file timed by hand is judged again from the video's stored clips, and keeps its ✓ only when it now fits. tv-srvr answers with the file's label as a play's list would give it, ✓ or not, and with whether the episode now counts as all checked; tvapp puts both on the track and the panel before it reloads, so Sync is allowed again when the file does not fit. The browser player's Apply changes its track's label the same way.

Below the offset are Sync on the left and Close on the right. Sync sends `sy`, and tvapp asks tv-srvr's `/api/measureSub` how far the showing file is off the words of the video (`measureSidecar()` in `subPrepare.js`). It judges the file from the video's stored clips. When the video has none, or has them for another audio track, it hears them first, which takes about ten seconds, and it hears a middle clip too when the file's two clips disagree; the clips and a verdict for a file that fits are all it stores. tvapp waits up to three minutes for the answer. For a video with no English audio it is the whole file's offset by audio matching, and no verdict is stored. The answer becomes the offset, just as if it had been set with the buttons, shown in hundredths, and the caption line above the offset shows the captions it puts at the video's position, so the timing can be checked by eye before Apply shifts the file. Nothing is written until Apply, but a file that already fits as it is gets its verdict, and its ✓, at once. The panel's labels are tv-srvr's, so a ✓ appears or goes as soon as tv-srvr answers. When the file is from another cut or runs at another rate, so no one shift fits it, or it can't be told or can't be checked, a toast on the TV says "Sync:" and why, and the offset is left as it was. A request that fails, which includes tv-srvr refusing while the sub queue is checking that video, gives the toast "Subtitle sync failed.". An answer that comes back after another track was picked is dropped. Sync needs a subtitle on, is grey while it or an Apply runs (a Sync or Apply sent then is ignored), and stays grey for an episode whose files have all been checked, which `getPlayUrl` reports. Holding the Apps key in tvapprc mode sends `k,reload`, which reloads the playing video the way Apply does, so a subtitle file edited by any other means can be picked up without stopping. The tvapprc bridge in tv-tv passes all of these messages through without reading them; while tvapp is not running they are simply lost.

## Browser players

The browser player at `/api/play`, opened in a new tab from the info and map panes, and from the local pane's Play for an episode file (`/api/play?path=`, which `getPlayUrl` turns into its episode), uses `getPlayUrl` just as tvapp does. It adds one subtitle track per sidecar and turns on the one at `subPick`. Switching tracks or turning them off is done with the browser's own captions menu. The subtitles are styled by the page: semibold white text, twice the normal size, on an opaque black box. It reports `playProgress` with the showing file as tvapp does, sending `device: "browser"`, but with its own states: a pause reports `playing`, and both the video's end and leaving the page report `stopped`, so the end counts as the end through the last-four-minutes rule. Its stops choose subtitles in the same way. It has no socket, so it never hears `subsLate`: a play that opened with no sidecars stays without subtitles until it is opened again.

At the top right, after a title chip with the show name and SxxEyy, a Subs button, left of Skip, opens and closes a timing bar at the top middle. Subs is there only when the play has sidecars, and Skip only when the season has a skip length. The bar holds −1, −0.5, the offset in seconds to one decimal, +0.5, +1 and Apply. Unlike tvapp, a move shows at once: the browser shifts the showing track's cues in place. Apply, grey until the offset differs from the one last applied, asks `/api/applySubOffset` to shift that sidecar on disk by the difference, just as tvapp does; the cues already match the file, so nothing reloads. A failed shift turns Apply's label to "Failed". Picking another track in the captions menu undoes any move not yet applied and resets the offset to zero. The bar's buttons work in fullscreen in the same way as Skip.

The web client also has an in-app video overlay, opened by the intro editor and by the local pane's Play for a movie. The intro editor's use shows no subtitles at all. For a movie it gets the sidecar list from `/api/subtitle-list`, starts on the first file, and shows a row of buttons, one per file plus "off". The active button has a white border, and its header, the file name, gets a note in parentheses naming whichever of SDH, CC, HI and FORCED appear in the active file's label or name. It sends no `playProgress` reports, so nothing it shows is remembered.

## Web client panes

The local pane's Subs button puts the selected videos at the front of the sub queue, without the naming instruction. A video already queued at normal priority stays where it is, and one whose entry is running is queued again once that run is done. Its entries count as manual, so the ASR they may lead to is not held to the daily limit. The button stays grey until tv-srvr reports back that each one is done, and then the file list is reloaded; for a video that was already queued at normal priority no report comes, so it stays grey until the page reloads. A video whose entry is running runs again afterwards, and reports then.

Its Sync button, between ASR and Fix, is enabled when one sidecar is selected that is not an `.asr.srt` and the video has an `.asr.srt`, even when the stored clips would be used. It moves that file to fit the video, by the video's stored clips when it has them, else by the median offset of short phrases (cues of one to four words, sound notes left out) that occur exactly once in both the file and the `.asr.srt`, needing at least ten such matches. By the clips it can stretch the file as well as shift it, refuses a file from another cut or with too few matching phrases, and stores the file's new verdict. A toast says how far the file was shifted and by how many phrases, or what went wrong.

this phrase method is the retime pass, run by hand on one file. It gains the rule that at least 80% of the matches lie within 250 ms of the median; otherwise the toast says the file is from another cut. The stored-clips path stays as it is.

Its EmbSub button opens a pane whose Apply copies out the selected videos' embedded text tracks directly, without the rest of the queue's steps; while it runs it can overwrite the stage text the Queues pane shows for a running sub entry. The pane's log shows each file as either already existing or newly extracted. The ASR button opens the ASR pane. Its Start button adds the selected videos to the ASR queue, where a video that already has an `.asr.srt` is skipped. Abort stops the running job, and Queue lists the queue with who added each entry and when; clicking an entry, after a confirmation, removes it, and removing the running entry kills it. Cost shows a month's bar chart of Speechmatics' cost per Los Angeles day. The ASR log streams live into the pane. EmbSub and ASR are also in the pane's movie mode, and neither checks for a movie, so a movie's tracks can be copied out and a movie can be sent to ASR from there. In season folders, the local pane's file tree lists subfolders first, then videos, then subtitle files (`.chosen` files among them), then everything else, the three file groups set apart by separators and each sorted by episode.

The Queues pane shows the sub, ASR and recode queues, polled every second. For the running sub entry it shows its current stage, one of "probing subtitle streams", "extracting embedded subs" with a count, "naming subtitle files", "checking subtitles", "checking subtitles by audio", "downloading subtitles" and "choosing next queue". The local file history view also lists subtitle events for a file: that it is queued for extraction or ASR, read from the live queue files, so the event shows only while the entry is waiting or running, and which ASR, OpenSubtitles and other subtitle files sit beside it, timed by each file's modification time. The watchdog heartbeat reports both queues' depths and completion counts, so a stuck queue can be told from an idle one.

The usb and local panes' file info lines show how many English or untagged embedded subtitle tracks a video has and how many `.srt` files sit beside it. The count includes bitmap and forced tracks, which are never copied out, so it can be more than the T and H files a video gets. The local pane counts with ffprobe, the usb pane from mediainfo's text sections.

The torrent pane's Chk Subs button asks tv-api to judge whether a torrent carries subtitles, three torrents at a time. tv-api says yes when the torrent's file list holds an `.srt`. Otherwise it reads the provider's page, which it can do only for IPTorrents and TorrentLeech: a MediaInfo text section or explicit wording says yes or no. A few release groups have known habits: the ones known to include subtitles give only "maybe", and MeGusta gives "no". Anything else is "maybe", and a torrent packed as rar archives gets "maybe" when the page found nothing. The button also counts OpenSubtitles results for each of the torrent's episodes through tv-srvr's `/api/subsCountEpisodes`, and the pane shows both answers on the torrent's row. Each count is the number of distinct releases on the first page of results, with a hearing-impaired copy of a release counted together with it, and the row shows the smallest count of any episode; an episode whose search fails counts as 0. The endpoint searches three episodes at a time. tv-api sends the IMDb id of the client's current show, else the show's name, which tv-srvr looks up among its own records, by exact name and then by a looser title match. With no id found that way, the search goes out by name as a movie, with no season or episode, so the count is not per episode. A search answered 429 is retried after the second it asks for, up to three tries in all. tv-api itself never talks to OpenSubtitles.

## Replacements, moves and cleanup

When a video loses to another copy of its episode, whether to a better download tv-down has just landed, to the duplicate-episode check or to the folder merger, it is deleted. `vidDeleteWithSidecars()` in `packages/share/src/videoFiles.js` deletes it together with every file starting with its name, except other videos and their own files, so the surviving video is never left beside another release's subtitles. tv-down deletes the file a download replaces only once the new file has landed whole (verified intact, even when rsync exited with an error), so a download that fails or never starts never costs the episode its video; it then deletes every other video in that season folder with the same SxxEyy. A replacement does not inherit the old video's subtitles, which were timed to the other release; it gets its own T and H copies, its own timing checks and downloads, and ASR when nothing fits. The one exception is a recode, whose output is the same cut under the same stem and keeps the sidecars (see above). A video rewritten in place under the same name keeps its sidecars too, but gets new T and H copies, and the rest are judged against it afresh (see above). No `.old` or `.alt` copies are kept. Quarantining a stray episode, from `/api/strayEpisodeQuarantine` or the map pane's Gapchk, moves it to `/mnt/media/tv-errors/<folder>/Season N/` and takes along every file whose name starts with its stem, so a video whose name extends that stem goes too. The folder merger moves every file across, sidecars included. Renaming files in the local pane does not take sidecars along.

tv-srvr's old-file cleanup runs at every start, so at every deploy, and then every seven days. It deletes orphaned sidecars from the show folders. These are files with a subtitle extension (srt, ass, ssa, asa, sub or idx) or one of a few metadata extensions, including the legacy `.chosen` markers and an episode's `.nfo` and `-thumb.jpg`, whose name does not start with the stem of any video in the same folder. Emby's show and season artwork and nfo files are never touched; its trickplay `.bif` files are deleted every run. Every delete is logged to `apps/srvr/data/auto-deleted-files.log`. An arrived `.srt` whose video never came is removed this way.

## Backfill

The backfill ran on 2026-10-11 from `apps/srvr/scripts/retime-backfill.js`, logging to `/tmp/retime-backfill.log` on hahnca.com. Its plan, as run:

**Scope.** Unwatched episodes only. A watched episode is never queued, retimed or downloaded for. The 18 videos that can't be matched to an episode record (Guilt S02 and S03, The Curse (UK)) are left alone too, their watched state being unknown.

On 2026-10-11, 1287 videos have an `.asr.srt`: 360 watched, 18 unmatched, 909 unwatched. Of the 909, 126 already have another file checked good and need nothing. 57 have no other subtitle file, so they download. The rest have other files on disk to try first.

**1. Build and deploy the change**, and give the subtitle summary in CLAUDE.md a line about the retime. Done 2026-10-11.

**2. Dry run.** `/api/subPrepare` with `dryRun` also reports what the retime pass would do (the file, its offset and match count, or why nothing fitted) and writes nothing. Run it on Anger Management season 2's unwatched episodes and read the report.

**3. One episode for real.** Queue S02E89 alone with the retime mark. It has only its `.asr.srt`, so the pass downloads. Play it in the browser player: it should start on the retimed file with a ✓, not on "+ ✓", and the wording and timing should be right near the start, in the middle and near the end. Don't let the play run to the end, which would mark the episode watched. Then do five more.

**4. The full run**, from a driver script, `apps/srvr/scripts/retime-backfill.js`.
- It runs on hahnca.com under nohup and logs to `/tmp/retime-backfill.log`. It never runs inside tv-srvr, since every deploy would kill it.
- It walks the library's season folders for videos with an `.asr.srt`, and skips any that is watched or unmatched, already has a retimes row, or already has another file checked good. It reads watched from tvdb.db, opened read-only, just before queuing each one, so an episode watched during the run is skipped too.
- It sends tv-srvr one video at a time over `http://127.0.0.1:8739`: `/api/asr/subs/enqueue` with `lowPriority` and `retime`. It waits until the entry has left the sub queue, reads the retimes row from subs.db (read-only), and moves on. While tv-srvr is down it waits and tries again.
- Order: the most recently played shows first; within a show, season and episode order, specials last.

**5. Pace and cost.**
- No daily cap: the entries run back to back.
- No Speechmatics calls at all. The retime mark runs the pass alone, and the pass reads the `.asr.srt`.
- Downloads come mainly from the 57 with no other file, at most five each: under 300 in all. The driver pauses when OpenSubtitles reports fewer than 200 downloads left for the day, so plays keep theirs.
- Time: a few seconds an entry, so about an hour. The sub queue runs these entries after other batch work, so a play pauses the run while its stills build.

**6. Report.** At the end the driver logs the counts: skipped (watched, unmatched, already done), already fine, retimed by type (T, H, V, S), nothing fitted, and errors. It stops early, and says why, if more than a tenth of its entries fail.

**7. Afterwards** nothing more is needed. New `.asr.srt` files and new arrivals get their passes from the watcher, and the retimes rows keep the queue from repeating a pass that found nothing.
