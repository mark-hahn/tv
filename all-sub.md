# Subtitles: how everything works

This document describes every piece of subtitle logic in the workspace as of 2026-10-02: where subtitle files come from, how they are named and cleaned, how one is chosen when a video plays, how the players show them and let you switch or retime them, and how they are cleaned up. It covers tv-srvr, asr, tv-down, tv-api, tvapp, the phone remote, the web tv pane, and the browser players.

## The one rule

Every subtitle that is ever shown is a sidecar `.srt` file sitting beside its video in the same season folder. Subtitle tracks embedded inside a video are never shown and never served to a player. When the video lands on disk, its English or untagged text tracks are copied out to sidecars. Bitmap tracks (PGS and the like), forced tracks and tracks in other languages are simply ignored. Every subtitle file written anywhere, for any reason, goes through `cleanSrt()` in `packages/share/src/srt.js` first. Movies get no subtitle processing at all.

## Cleaning a subtitle file

`cleanSrt()` takes the raw text of a subtitle file and returns the cleaned text. When nothing needed fixing it returns the text exactly as it came. Cleaning first strips formatting: anything in curly braces (ASS override codes), anything in angle brackets (HTML-style tags such as italics and font colors), the ASS hard space, which becomes a plain space, and the ASS line-break codes, which become real newlines. It then parses the file into cues, keeping only blocks that have a time line and some text, and accepting either a comma or a period before the milliseconds. It sorts the cues by start time, because extraction from embedded tracks can produce them out of order, and merges cues that have exactly the same start and end into one cue whose lines are stacked.

The last step undoes "rolling" subtitles, a format that blinks on screen. Back-to-back cues with identical text and less than 250 ms between them are merged into one. If at least three of the remaining cues, and more than 15 percent of them, are shorter than 250 ms, the file is treated as rolling. Every such short cue that shares a line of text with the cue just before or just after it (within 500 ms) is then dropped, since it is only a transition between two real cues. If anything at all changed, the cues are renumbered from 1 and written back out in standard SRT form, with a comma before the milliseconds.

## Names and types

A sidecar belongs to a video when its name is the video's name without its extension (and without a trailing `.alt`), followed either directly by `.srt` or by a dot, a suffix and `.srt`. The suffix is whatever sits between the video's stem and `.srt`, and it decides the sidecar's type (`sidecarType()` in `apps/srvr/src/subOrigin.js`).

There are five types. A suffix of T followed by a number is a copy of the video's own embedded text track with that stream index, type T. The legacy name `mb` followed by a number also counts as T. H followed by a number is the same kind of copy, but of a track flagged as describing music and sound (SDH), type H. `opn` followed by five characters is an OpenSubtitles download, type V; the five characters are the OpenSubtitles file id written in base32 using the letters A to Z and the digits 2 to 7, padded on the left with A. The suffix `asr` is a transcript made by speech recognition, type "+". Anything else is type S: S followed by a number is a subtitle file that arrived beside the video and was renamed by tv-srvr. A bare `<stem>.srt`, or something like `<stem>.en.srt`, also counts as S.

Each sidecar also gets a short label for the subtitle panels (`sidecarLabel()`). It is the type letter and the number, such as "T 3", "H 4" or "S 1". A download shows as V and its tag, such as "V CYR4Q", and an ASR file shows as a lone "+". An S file with an odd suffix shows as S followed by that suffix.

`listSidecars()` in `apps/srvr/src/subs.js` lists a video's sidecars in a fixed order: T first, then H, V, S and finally +. Within a type the files are in natural filename order. This list is what every player is offered, and the order is also the fallback preference when nothing else decides which subtitle to start on.

Sidecars that tv-srvr names itself (T, H, `mb`, S with a number, `opn` and `asr`) are recognised by `NAMED_SIDECAR_RE` in `apps/srvr/src/subsQueue.js`. Any other `.srt` that appears in a show folder is treated as a newly arrived file that still needs naming.

## The subtitle database

`apps/srvr/data/subs.db` is a SQLite database owned by `apps/srvr/src/subs.js`, and tv-srvr is its only writer. It has three tables.

The subs table holds every result an OpenSubtitles search has ever returned for an episode. Each row is keyed by show id (the TVDB id), season, episode and OpenSubtitles file id. Rows keep the order in which the searches first returned them. Each row records the result's flags (hearing impaired, hd, foreign parts only, AI translated, machine translated), its frame rate, uploader id, upload date, release name, comments and episode title. It also carries two markers: downloaded, set once the file is on disk beside the video, and chosen, set on the download that was showing when the episode was last stopped.

The picks table holds, for each episode, the sidecar that was showing at its last real stop: its suffix, its type and a timestamp. The processed table holds the paths of videos that have been through the add-to-disk steps described below.

## When a video lands on disk

tv-srvr watches `/mnt/media/tv` with chokidar. It ignores dot files and waits until a file has stopped growing for two seconds. When a video file appears, the show's disk cache is updated, and the new files for that show are gathered for a short debounce. They are then handled only if the show has a TVDB record and is in the library; otherwise a log line notes that the files skipped the subtitle queue.

Each new video first goes through two checks. If another active (not `.old`) video of the same episode is already present, and both resolutions are known and differ, the lower-resolution one is demoted to `.old` together with its sidecars, and if the new file is the loser it is not queued. If the video is one the TV player stalls on (a DivX-tagged mpeg4 file), it goes to the recode queue instead. The recode writes an h264 mkv with the same stem, discarding embedded subtitle streams, and that output then arrives as a fresh add and takes the normal path. Every other new video is put on the sub queue with the instruction to name any arrived subtitle files.

The sub queue is a list of entries persisted to `apps/asr/data/subQueue.json`. Queuing a video already in the list never adds it twice. A second request merges into the first: a request to name arrived files carries over, and a normal-priority request moves a low-priority entry to the front. Requests from the web client's local pane go to the front. A loop checks the queue every 10 seconds when it is empty and every half second while it has work. Entries are processed strictly one at a time. An entry stays in the queue while it runs and is removed when it finishes, even if it fails; if tv-srvr is killed in the middle, the entry is still in the file and runs again after a restart. Every step skips work that is already done, so running an entry twice is harmless.

Processing one entry goes like this. If the video file is gone (most often because it was demoted to `.old`), the entry is dropped. If it is under `/mnt/media/movies`, it is dropped with a log line, because movies get no subtitle processing. Otherwise the season and episode are parsed from the file name and the show's record is looked up.

The first step copies out the embedded text tracks. ffprobe lists the video's streams. If ffprobe fails, the entry ends with an error and is not marked processed, because treating a failed probe as "no embedded subtitles" would send a video with perfectly good tracks off to paid ASR; the sweep will bring it back later. A stream is copied out when it is a subtitle stream in a text format (subrip, ass, ssa, webvtt, mov_text, text or srt), its language tag is English or missing, and it is not flagged as forced. Each such stream becomes `<base>.T<n>.srt`, or `<base>.H<n>.srt` when it is flagged as hearing impaired or its title contains "SDH", where n is the stream index. Nothing is written when that file, or the legacy `<base>.mb<n>.srt`, already exists. ffmpeg converts the stream to SRT, running in the idle CPU and idle disk class, through a small serial queue shared by every extraction so a whole season can't start a crowd of ffmpegs at once. The result is written through `cleanSrt()`, and only when the output contains at least one time line. This step also notes whether the video has any such text track at all, whether or not a copy was needed.

The second step, for videos that parse to a season and episode, gives arrived subtitle files their names. It looks at every non-hidden `.srt` in the folder that is not already a named sidecar and not another video's own file, and that parses to the same season and episode. Each is cleaned and added as the video's next S file, numbered one past the highest S number there. If an existing S file already has exactly the same text, the new one is a duplicate and is not added. Either way, the original file is deleted.

The third step takes over the subtitles of a video this one replaced. A replaced video is one of the same season and episode, with a different stem, that has been stepped aside with one or more `.old` suffixes. Its sidecars may have moved to `.old` with it or been left under its old name; both forms are found. Each is cleaned and copied. A T, H, V or ASR file keeps its suffix under the new stem, unless a file of that name already exists. An S file, or anything else, becomes a new S file under the same duplicate rule. The old video's T and H copies come over only when the new video has no embedded text tracks of its own, because otherwise the new video's own copies are the right ones. The old files are left where they are.

The fourth step searches OpenSubtitles, but only for an episode of a show whose record has an IMDb id. Nothing is downloaded here; the results are stored in subs.db. A result whose file is already on disk as an `opn` sidecar is marked downloaded at the same time. If the search fails, the entry ends without being marked processed and without going to ASR, since ASR costs money and whether the video needs it is not known until a search works. The sweep brings such videos back. When the search works, tv-srvr asks whether the episode has a usable subtitle, meaning one already downloaded or one the download rules below would pick.

The last step decides about ASR. The video goes on the ASR queue when it has no embedded text track, the search found nothing usable (or no search could be made), and it has no subtitle file of any type beside it (including an `.asr.srt`). Finally the video is marked processed.

## Subtitle files that arrive on their own

When the watcher sees a new `.srt` that is not a named sidecar, in the folder of a library show, it parses the season and episode from the file name (using the folder name as a hint). It then looks for the active video of that episode in the same folder. If one is there, that video goes on the sub queue with the naming instruction, and the second step above turns the file into an S file. If the video is not there yet, nothing happens now; when the video arrives, its own trip through the queue picks the file up.

tv-down brings `.srt` files over from the usb seedbox. It takes one only when its episode's video is already on disk, or is being downloaded or queued in the same cycle, and it puts the file in the show's season folder under its original name. Where the name has no SxxExx marker it becomes "show folder SxxExx.srt", and an NNN or NxN episode number is rewritten the same way. tv-down never cleans or renames the file further; that is left to tv-srvr. An arriving `.srt` never makes tv-down demote anything to `.old`, and it is exempt from the video quality and duplicate rules. A forced download skips the video check entirely. An `.srt` whose name and top folder give no season and episode is skipped with a log line, never an error entry. Such files usually share names like `2_eng,English.srt`, so one error entry would block all the others. Movie downloads copy video files only, never subtitles.

## The backstop sweep

The watcher is the only normal path into the sub queue, and it once silently lost every download for shows whose folder name differs from their TVDB name. So a second path walks the whole library: 10 minutes after tv-srvr starts and then every 6 hours. It queues, at low priority, every video of a library show that is not already in the sub or ASR queue, has not been processed, has no sidecar at all, and is not marked watched. This is also how videos that were on disk before the queue existed get their embedded tracks copied out. A settled library adds nothing, so the sweep is just a directory walk.

## ASR

The ASR queue is persisted to `apps/asr/data/asrQueue.json`, and a video is never in it twice. Videos reach it from the sub queue's last step, from the web client's ASR pane, or through the ASR enqueue endpoint. A loop runs one job at a time: it checks every 10 seconds when the queue is empty and every half second while it is working. A job whose video is gone, or that already has an `.asr.srt`, is skipped with a log line.

A job runs `apps/asr/asr.js` as a child process in the idle CPU and idle disk class. It passes the video's path and a vocabulary list built from the show's TVDB character names: each full name, with titles such as Dr, Nurse, Lt, Mr, Mrs and Ms removed, plus every word of it longer than two letters. asr.js extracts the video's first audio track as mono 16 kHz FLAC and uploads it to Speechmatics as a batch job, in English, with the "enhanced" operating point and the names as additional vocabulary. It polls every 5 seconds, giving up after 240 polls. Failed requests and HTTP 429, 500, 502 and 503 answers are retried up to five times, with waits that double from 5 seconds. The json-v2 transcript gives every word its measured start and end, and punctuation is glued onto the word before it.

Cues are built from those word timings. A new cue starts at a gap in the speech longer than one second, when the next word would push the text past 84 characters, or after a sentence end once the cue holds at least 28 characters. A cue that is still too long is split at sentence ends, then clause ends, then word boundaries, and each piece gets the real times of its own words. Each cue is wrapped onto at most two lines of at most 42 characters, breaking preferably after punctuation and otherwise where the two lines come out most even.

The timings are then made readable. A cue's reading time is its length at 16 characters a second, kept between 0.35 and 12 seconds. A cue that would stay up longer than two and a half times its reading time plus a second is cut back to 1.6 times its reading time plus 0.4 seconds. Cues that start less than 0.45 seconds apart are merged when the joined text fits. After that, every cue starts at least 0.98 seconds after the one before it. Each cue is held for at least 0.9 seconds and never less than 0.35, and it ends 80 ms before the next one starts. Stretches of 30 seconds or more with no speech are reported in the log. The result is written through `cleanSrt()` as `<stem>.asr.srt`, and the temporary audio file is deleted.

Everything the job prints goes to a buffer shown in the ASR pane, to `apps/asr/data/subtitle.log`, and to the web client. The log is rotated daily at 5 am Los Angeles time into `subtitle-logs/subtitle-MM-DD.log`. The Queues pane's stage text ("extracting audio", "uploading audio", "transcribing", "retrying", "writing subtitles") is read off those printed lines, and its ETA is a flat 60 seconds per job. A job can be aborted, which sends SIGTERM to asr.js; asr.js then kills its own ffmpeg and exits, and the log records the job as cancelled. Removing the running entry from the queue aborts it in the same way. While the ASR queue is not empty, the client header shows "Asr:" and the queue's length.

## OpenSubtitles

tv-srvr talks to the OpenSubtitles REST API in `apps/srvr/src/opensubtitles.js`, using the API key, username and password in its secrets folder and a fixed "tv-srvr v1.0.0" user agent, because the API rejects generic ones. The login token is cached in the secrets folder. At startup it is renewed when it is missing, expired, or within a day of expiring. A search answered with 401 or 403 logs in again and retries once. A search asks for English subtitles for the show's IMDb id, season and episode, and only the first page of results is used. A download first asks the API for a link to the file and then fetches it. The link request is tried up to three times on 502, 503 and 504 answers or network errors, waiting a little longer each time. A 429 answer, the API's limit of five requests a second, is retried after the one second its retry-after header asks for.

Nothing is ever downloaded from OpenSubtitles except just before a video plays (`subsBeforePlay()` in `subs.js`), and this is the same for tvapp and the browser player. If the episode already has three downloaded files, nothing happens. If the show has no IMDb id, nothing happens beyond a log line. Otherwise a fetch job starts, unless one is already running for that episode, in which case that job is shared. The job searches again, storing any new results. It then downloads all the candidates the episode still needs at once, and replacements for any that failed, until the episode has three downloads, three downloads have failed, or no candidate is left.

The candidate is the first not-yet-downloaded result, in the order the searches returned them, that comes from the same origin as any file chosen for any episode of the show. Failing that, it is the first one that is not foreign-parts-only. Each download is written through `cleanSrt()` as `<stem>.opn<TAG>.srt` and marked downloaded.

The play waits for the job for at most 3 seconds. If the job takes longer, the video plays anyway, the job carries on in the background, and the files it finishes are there the next time. In that case, when any search or download failed, or when the video has no subtitle file at all once the wait is over, tv-srvr sends a `subError` message to every client. All of these go into one message. The phone shows it as a pink pop-up box over a dimmed screen, and the web client shows the same box over everything, whichever pane is open. The text names the show and episode and says that the download took more than 3 seconds, what failed, or "no subtitles", separated by semicolons. The pop-up stays until its Close button is pressed, and a newer error replaces the text. On the phone it sits above every screen, the subtitle panel and the other full-screen views included.

## Same origin

Two OpenSubtitles results for different episodes of a show are said to come from the same origin when a choice made on one should carry over to the other (`sameOrigin()` in `subOrigin.js`). Their five flags must match: hearing impaired, hd, foreign parts only, AI translated and machine translated. Their frame rates must be equal unless either one is unknown (zero).

When both were uploaded by a real person, they must have the same uploader and upload dates within an hour of each other, since that is one person's batch. When either uploader is one of the shared bot accounts (os-auto 3282, os_robot 119465 and system 2), whose uploads are imports from everywhere and whose dates are import dates, the release names are compared instead. Each name is lower-cased, its punctuation is turned into spaces, and the episode marker (SxxEyy, NxNN, "episode N" or the bare season-and-episode number) and the episode's title are taken out. The two results match when what is left is equal and not empty, or else when their comments are equal and not empty. `apps/srvr/scripts/check-sub-origin.js` checks these rules against real search results.

## Which subtitle a video starts on

When tvapp or the browser player asks tv-srvr's `getPlayUrl` what to play, the reply lists the episode's sidecars in panel order. Each entry carries a URL that serves the file as WebVTT, the panel label and the file name, together with `subPick`, the index of the one to start on (`pickSidecar()`), or -1 when there are no sidecars. Embedded tracks are never in the list.

The first choice is the file this episode itself last showed, if that file is still on disk. Failing that, tv-srvr takes the type of the subtitle the show most recently showed in any episode. If that type is V, it looks for a downloaded file of this episode whose search result comes from the same origin as any chosen file of the show. Otherwise, or if no such file exists, it takes the first sidecar of that type. When the show has no history at all, or has none of that type here, the first sidecar in the list is used, so the order T, H, V, S, + is the default preference. Turning subtitles off is never remembered: a stop with subtitles off records nothing, so the next play starts with subtitles on again.

## Which subtitle a video stopped on

Both tvapp and the browser player send the file name of the subtitle currently showing, or an empty string when subtitles are off, in every `playProgress` report. tv-srvr acts on it only at a stop. A stop counts if it is an explicit stop, the end of the video, or a stop within the last four minutes, which counts as the end. A stop in the first 10 seconds counts as never having played, and it chooses nothing. At a counted stop with a subtitle showing, that file becomes the episode's pick in the picks table, with its type and the current time. If it is a download, its search result becomes the episode's only chosen row; if it is any other type, none of the episode's rows stay chosen. The pick decides where this episode starts next time, the type and timestamp steer the show's other episodes, and the chosen rows steer which downloads are tried first for the rest of the show.

## Serving subtitles to players

`/api/subtitle` takes a video path and a sidecar file name, and the path must be under the TV or movies folder. It reads the `.srt`, changes the comma before the milliseconds to a period, puts a WEBVTT header on top, and returns it with no caching, so an edited file is always fetched fresh. It serves the file exactly as it is on disk; a timing change exists only as an edit to the file itself. `/api/subtitle-list` lists a video's sidecars with their labels, for the web client's in-app player.

`/api/stream`, the browser's video stream, can still burn a bitmap subtitle stream into the picture when asked for a stream index, but no caller asks for one, so embedded subtitles are never shown that way either.

## tvapp

tvapp's `VideoPlayer` (Media3 ExoPlayer) adds every sidecar from `getPlayUrl` as a side-loaded WebVTT subtitle with its panel label. The tracks get no language and no default or forced flags. When the tracks first become known, it turns on the one at `subPick`; if there is none, it turns the text track type off altogether. Because text is either forced onto a side-loaded track or switched off entirely, Media3 can never fall back to a track embedded in the file, and only the side-loaded tracks are ever offered for selection. Subtitles use Media3's default look; tvapp sets no size, color, position or background. Trailers play with captions off.

tvapp sends the remote the subtitle list as `l,` followed by JSON. The JSON holds a title made of the show name and the SxxEyy code, the tracks (each with its label and the type "srt"), the index of the selected track or -1, and two numbers for the timing offset described below. The list goes out every time the player's tracks change, whenever the offset moves, and whenever the remote asks with `l`. When a video closes, tvapp sends `l,null`; playing another episode closes the first, so a null list is sent before the new one. A `t,<n>` command turns on track n, and `t,-1` (or any number out of range) turns subtitles off. Choosing a different track resets the offset to zero.

While a scrub hold is on, the full-screen stills cover the video and its subtitles until the hold has landed. The camera overlay does not change the subtitles, and subtitle commands still work while it is up.

## The subtitle panel on the remotes

In tvapprc mode, holding Vol+ for 400 ms on the phone remote or in the web tv pane opens the subtitle panel; a shorter press is an ordinary volume step. Outside tvapprc mode, holding Vol+ just turns the volume up one step. The phone does not open the panel in the "linda" layout, and the web pane does nothing at all while the TV is off.

Opening the panel sends `l`, and the panel shows the most recent list tvapp has pushed. Lists keep arriving whether the panel is open or not, and the panel always shows the newest. Its header is the video's title, or "No video playing" when the list is null. The body is a grid of buttons: "None" first, then one button per track showing its label, with the selected one shaded light blue and in bold. Tapping a track sends `t,<n>`, and tapping None sends `t,-1`. The tap marks the selection at once and the next list from tvapp confirms it. Tapping does not close the panel. Only its Close button does, and the panel stays open (with its last list) even when the video stops or tvapprc mode ends.

Below the grid is the timing offset. It shows the offset in seconds, beside an Apply button and two rows of buttons that move it by one second or half a second either way. Each move is sent to tvapp as `so,` and the number of seconds, and tvapp adds it to its offset and sends the list back. Nothing is shifted until Apply, which is enabled only when a track is selected and the offset differs from the one last applied. Apply sends `sa`. tvapp then asks tv-srvr's `/api/applySubOffset` to shift the selected sidecar on disk by the difference between the current offset and the last applied one, in milliseconds. tv-srvr moves every cue's start and end by that amount, never below zero, and writes the file back through `cleanSrt()`. When the shift succeeds, and the same video is still up, tvapp reloads the video at the same position, keeping the same track, so the edited file is fetched again.

The shift is permanent and applies to everyone who plays that file afterwards. Holding the Apps key in tvapprc mode sends `k,reload`, which reloads the playing video in the same way, so a subtitle file edited by any other means can be picked up without stopping. The tvapprc bridge in tv-tv passes all of these messages through without reading them; while tvapp is not running they are simply lost.

## Browser players

The browser player at `/api/play`, opened in a new tab from the info and map panes, and from the local pane's Play for an episode file (`/api/play?path=`, which `getPlayUrl` turns into its episode), uses `getPlayUrl` just as tvapp does. It adds one subtitle track per sidecar and turns on the one at `subPick`. Switching tracks or turning them off is done with the browser's own captions menu, and the subtitles use the browser's default styling. It reports `playProgress` with the showing file just as tvapp does, so its stops choose subtitles in the same way.

A Subs button, left of Skip at the top right, opens and closes a timing bar at the top middle: −1, −0.5, the offset in seconds, +0.5, +1 and Apply. Unlike tvapp, a move shows at once: the browser shifts the showing track's cues in place. Apply, grey until the offset differs from the one last applied, asks `/api/applySubOffset` to shift that sidecar on disk by the difference, just as tvapp does; the cues already match the file, so nothing reloads. A failed shift turns Apply's label to "Failed". Picking another track in the captions menu undoes any move not yet applied and resets the offset to zero. The bar's buttons work in fullscreen in the same way as Skip.

The web client also has an in-app video overlay, opened by the intro editor and by the local pane's Play for a movie. The intro editor's use shows no subtitles at all. For a movie it gets the sidecar list from `/api/subtitle-list`, starts on the first file, and shows a row of buttons, one per file plus "off". The active button has a white border, and the active file's label is added to the file name in its header with an SDH or CC note where the label or file name says so. It sends no `playProgress` reports.

## Web client panes

The local pane's Subs button puts the selected videos at the front of the sub queue. The button stays grey until tv-srvr reports back that each one is done, and then the file list is reloaded. Its EmbSub button opens a pane whose Apply copies out the selected videos' embedded text tracks directly, without the rest of the queue's steps. The pane's log shows each file as either already existing or newly extracted. The ASR button opens the ASR pane. Its Start button adds the selected videos to the ASR queue, Abort stops the running job, and Queue lists the queue with who added each entry and when; clicking an entry removes it, and removing the running entry aborts it. The ASR log streams live into the pane. In season folders, the local pane's file tree lists videos first, then subtitle files, then everything else.

The Queues pane shows the sub, ASR and recode queues, polled every second. For the running sub entry it shows its current stage, one of "probing subtitle streams", "extracting embedded subs" with a count, "naming subtitle files", "searching opensubtitles" and "choosing next queue". The local file history view also lists subtitle events for a file: when it was queued for extraction or ASR, and which ASR, OpenSubtitles and other subtitle files sit beside it. The watchdog heartbeat reports both queues' depths and completion counts, so a stuck queue can be told from an idle one.

The usb and local panes' file info lines show how many English or untagged embedded subtitle tracks a video has and how many `.srt` files sit beside it. The torrent pane's Chk Subs button asks tv-api to judge whether a torrent carries subtitles. tv-api says yes when the torrent's file list holds an `.srt`. Otherwise it reads the provider's page: a MediaInfo text section or explicit wording says yes or no, and a few release groups have known habits. A torrent packed as rar archives can't be verified. The button also counts OpenSubtitles results for each of the torrent's episodes through tv-srvr's `/api/subsCountEpisodes`, and the pane shows both answers on the torrent's row. Each count is the number of distinct releases, with a hearing-impaired copy of a release counted together with it, and the row shows the smallest count of any episode. The endpoint searches three episodes at a time and finds the show's IMDb id by name when tv-api has none. A search answered 429 is retried after the second it asks for. tv-api also has its own OpenSubtitles search proxy, which downloads nothing.

## Replacements, moves and cleanup

When a video is stepped aside to `.old`, whether by the duplicate-episode check, the folder merger or tv-down's "usb copy is better" path, `vidDemoteToOld()` in `packages/share/src/videoFiles.js` takes every file starting with the video's name, except other videos, along with it. That way the surviving video is never left beside another release's subtitles. tv-down's own rename at the start of a replacement download moves only the old video and leaves its sidecars where they were. The replacing video's trip through the sub queue then copies either form over, as described above. Moving a stray episode to another folder takes its sidecars with it. Renaming or swapping files in the local pane does not take sidecars along.

Once a week, tv-srvr's old-file cleanup deletes orphaned sidecars from the show folders. These are files with a subtitle extension (srt, ass, ssa, asa, sub or idx) or one of a few metadata extensions, including the legacy `.chosen` markers, whose name does not start with the stem of any video in the same folder. A video's `.old` and `.alt` suffixes are ignored when its stem is worked out, so a stepped-aside video keeps its sidecars. Emby's own metadata files are never touched, and every delete is logged to `apps/srvr/data/auto-deleted-files.log`. An S file that arrived for a video that never came is removed this way.

## Loose ends found while writing this

tv-down cannot take the common layout of subtitles inside a release, `Subs/<episode folder>/2_eng,English.srt`. The episode is only in the parent folder's name, which tv-down does not parse, and every such file has the same name, which tv-down uses as its key.

`/api/stream`'s bitmap burn-in is not used by any player.
