
# unilog: universal logging

- unilog will replace most logging in the app, both server and client
- all logging is managed in db /root/dev/apps/tv/unilog/unilog.sqlite
  - it keeps track of all source code logging locations in table log_sites
  - all log execution is stored in table log_events 
  - later there will be a log viewer in a tab pane
    - it will access the db to display logging results
- it consists of 2 parts
  - unilog tooling
    - this is tooling that adds calls to source code
      - copilot chat adds log sites to source code based on prompts
      - there is a unilog agent to automate the actual editing
    - unilog reconciling happens at:
      - code deployment
      - when processes are started in the server
  - unilog logging
    - when app code runs the log sites are calls to the runtime unilog routines
    - there are client and server routines that centralize writing to the db

## nomenclature
- the loggin feature was originally called "universal logging"
- it is now called unilog

##  unilog groups
- this is a new feature
  - you can decide if it is a good feature
  - if you don't like it you can ignore these instructions
- a new table log_groups should be added to the db
- most log_sites table entries will reference a group. groups represent these types of collections of call sites:
  - sites added from one copilot prompt
  - sites added from one copilot conversation
  - sites that track program flow
    - e.g a flow from a button press to the matching action
  - sites in a source file like tvdb.js
  - sites in a server task like tv-down and tv-srvr
- some of the table fields are:
  - group_id: a unique integer id for each group
  - ts: date/time group was created. format is 'yyyy/mm/dd hh:mm:ss' 
  - group desccription: describes the group
    - can be generated by copilot from log site code context
    - can be a prompt from the user that creates log site(s)
    - can be instructions from a conversation to an agent
- this is mostly meant for use by the log viewer

## type of logging sites
1. traditional writes like console.*
  - these will eventually be replaced with unilog calls
2. traditional writes with blocking comment
  - the old-style log site will have a comment '// no-unilog' at end of logging source line
  - it means that unilog should not replace or add a log call
    - this is for debugging unilog itself
    - short-term old-style logging
3. a unilog call site stub
  - when the agent adds a unilog call it will be commented out like '// unilog-stub: unilog(<logging site params>);
  - this is written while editing source file
  - in the reconciliation process on deploy or process start this will be turned into an active log site by removing '// unilog-stub: ' and and log site will be added to db
  - this solves the problem of ensuring db always matches active calls
4. an active unilog call site
  - this is what logs the log event into the db
  - the centralized function is called unilog

## existing log handling
- when a unilog call stub or active call is added to source any existing old-style logging at the same site is removed
- there will never be a traditional call next to a new unilog call at any phase of development
- unilog calls will never append to any old log file

## no Normalized log objects
- the concept of a Normalized log object is vague and not useful
  - it is replaced with a combination of log_site and log_event db table entries
  - if needed it can be used ephemerably in code

## Scope decisions
- the unilog folder is also excluded
  - unilog tooling will use traditional writes with blocking comment
