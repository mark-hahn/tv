# Universal Logging — Implementation Plan

Goal: mirror **all** application logging into one central, machine-readable store on
the remote server, while leaving the existing log destinations (pm2 stdout logs,
`subtitle.log`, `tv.log`, `tv-adb.log`, etc.) untouched. No store reader is built
yet — a log-viewer tab pane comes later.

This document is a plan only. No code has been changed (only `temp.md` stats and
this file were written).

---

## 1. Current logging landscape (from `temp.md`)

- ~**1,208** log call sites across **111** files / **80,450** lines.
- Heaviest: `apps/srvr/index.js` (289), `apps/tv/src/main.js` (96, via `log/loge`),
  `apps/client/src/emby.js` (76), `apps/api/src/server.js` (68),
  `apps/client/src/components/list.vue` (63).
- Logging styles in use:
  - **`console.*`** everywhere — captured by pm2 into `*-out.log` / `*-error.log`.
  - **srvr** `logSubtitle()` → appends `apps/asr/data/subtitle.log`.
  - **tv** `log()` / `loge()` wrappers → `console.*` (+ adb write stream).
  - **down** `tvJson.js` → appends `misc/tv.log`.
  - Most lines carry a `[tag]` prefix (`[bif]`, `[asr]`, `[subs]`, `[TV ...]`, …).
- **pm2 processes** (separate OS processes, one DB writer problem — see §4):
  `tv-api`, `tv-down`, `tv-srvr`, `tv-tv`; plus `tv-srvr` spawns `asr` workers and
  `tv-down` spawns workers.

## 2. Store choice — SQLite (decided)

**Decision: SQLite** at `/root/dev/apps/tv/logs/all-logging.sqlite` (confirmed).

- Machine-readable and trivially scannable by Copilot chat (`sqlite3 ... "SELECT …"`).
- No daily rotation needed.
- Cheap structured queries by tag, file, level, time — ideal for the future log pane.
- WAL mode + `busy_timeout` so the future log pane can read while the writer writes.

Schema:

```sql
CREATE TABLE IF NOT EXISTS log_sites (   -- one row per source call site
  log_id      INTEGER PRIMARY KEY,        -- unique integer logging id (never reused)
  tag         TEXT,                       -- short tag, e.g. "bif"
  description TEXT,                        -- short flow description (agent-generated; optional)
  src_file    TEXT,                        -- path of source file
  src_line    INTEGER,                     -- line number (refreshed on deploy; may drift)
  old_log     TEXT,                        -- existing log file the legacy call targeted
  project     TEXT,
  removed_at  TEXT                          -- tombstone (NULL = active)
);

CREATE TABLE IF NOT EXISTS log_events (  -- one row per runtime emission
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  log_id    INTEGER,                       -- FK -> log_sites.log_id
  level     TEXT NOT NULL,                 -- 'debug'|'info'|'warn'|'error' (error decided at read time)
  pid       TEXT,                          -- emitting process, e.g. 'tv-srvr'
  ts        TEXT NOT NULL,                 -- 'yyyy/mm/dd hh:mm:ss' PST
  message   TEXT NOT NULL                  -- full message text (never truncated)
);
CREATE INDEX IF NOT EXISTS idx_events_logid ON log_events(log_id);
CREATE INDEX IF NOT EXISTS idx_events_ts    ON log_events(ts);
CREATE INDEX IF NOT EXISTS idx_events_level ON log_events(level);
```

- **No `is_error` column** — `level` discriminates; "is this an error" is decided when
  reading/displaying (confirmed).
- **`pid`/process** column identifies which pm2 app emitted the event.
- **Message size is not capped** in the DB (confirmed). Over-long existing messages are
  shortened at the source first — see §8 and `temp2.md`.
- `log_sites` **is** the registry; there is no separate `logRegistry.json` (see §3).

## 3. The registry = the `log_sites` table (no separate JSON file)

You asked why a `logRegistry.json` is needed. **It isn't** — `log_sites` already holds
everything (`log_id`, tag, description, src_file, src_line, old_log, project). So:

- **`log_sites` is the single source of truth.** No `logRegistry.json` file.
- **Id allocation** comes from the DB: next id = `SELECT max(log_id)+1`. Option A has
  one DB owner in srvr, and the log-agent already ssh's to the DB, so a local file
  buys nothing. Ids are allocated once and **never reused** (confirmed).
- **Line numbers are refreshed directly into `log_sites`.** A deploy-time pass (and the
  log-agent after each edit) re-scans `// log-id:` comments and `UPDATE`s `src_line` in
  the DB — no intermediate file. Drift between passes is acceptable.
- Each instrumented call site carries a trailing `// log-id: <n>` comment so a row can
  be traced back to source.
- **Descriptions are generated by the log-agent**, not from static context, and only
  where useful (busiest sites first — see §6); the agent fills the rest as logs are
  added/edited.

> Trade-off of dropping the JSON: `log_id -> location` lookups and code-review diffs now
> need the DB (or the query helper, §10) rather than a git-tracked file. Given Option A
> and the agent's DB access, that's an acceptable loss; a read-only export can be
> regenerated on demand if offline lookup is ever wanted.

## 4. Architecture — how lines reach the store

The instruction says "server files should send log lines to a common routine that
writes to log store" and "client → shared client routine → server endpoint → server
common routine". Two viable shapes for the multi-process server side:

- **Option A (DECIDED): one collector owns the DB.**
  A single writer (in `tv-srvr`) owns `all-logging.sqlite`. The shared "common
  routine" (in `@tv/share`) writes **directly to the DB only inside `tv-srvr`**; the
  other processes (`tv-api`, `tv-down`, `tv-tv`, asr/down workers) call the same
  routine which **POSTs** the event to a srvr endpoint `POST /api/log`. This avoids
  multi-process SQLite write contention and matches the client path exactly (client
  also POSTs to `/api/log`). One code path, one writer.

- **Option B (rejected): every process writes the DB directly** using WAL mode +
  `busy_timeout`. Simpler wiring, but 5+ concurrent writers risk lock churn and make
  the "common routine" subtly different from the client path.

Recommended flow:

```
client routine  ─POST /api/log─┐
tv-api  routine ─POST /api/log─┤
tv-down routine ─POST /api/log─┼─►  tv-srvr  /api/log  ─►  common writer  ─►  SQLite
tv-tv   routine ─POST /api/log─┘                                   │
tv-srvr routine ───────────────────────in-process call────────────┘
```

Shared routine responsibilities (single function, e.g. `logEvent(logId, level, message)`):

1. Build normalized object (PST timestamp `yyyy/mm/dd hh:mm:ss`, `log_sites` lookup).
2. Persist to store (direct in srvr, POST elsewhere).
3. **(Transitional) also perform the original write** (call the real `console.*` /
   append to the old log file) so existing destinations keep working until legacy
   file logging is removed per project.

Failure isolation: store/POST failures must never throw into business logic —
swallow + best-effort, so logging never breaks the app.

### Client specifics

- Add a shared client routine (new `apps/client/src/log.js`) that POSTs to
  `/api/log` (batched, fire-and-forget). All `console.*` in client code route
  through it (it still calls `console.*` so the browser console and
  `apps/client/vite-console.log` mirror are unaffected).
- Batch + `navigator.sendBeacon` on unload to avoid flooding and lost tail events.

### Server endpoint

- `POST /api/log` on `tv-srvr` validates `{ logId, level, message }`, applies the
  PST timestamp + `pid` server-side, and calls the common writer. (Reuse existing
  express + CORS already in srvr.)

## 5. Normalized log object (per instruction)

```jsonc
{
  "logId": 412, // unique integer per source location
  "level": "info", // debug|info|warn|error (error decided at read time)
  "pid": "tv-srvr", // emitting process
  "timestamp": "2026/06/27 14:05:31", // PST, yyyy/mm/dd hh:mm:ss (date-only -> 00:00:00)
  "tag": "bif", // short tag (was "[bif]")
  "description": "queue bif build for show", // agent-generated, optional
  "srcFile": "apps/srvr/index.js", // source path
  "srcLine": 1127, // line number (refreshed on deploy; may drift)
  "oldLog": "/root/.pm2/logs/tv-srvr-out.log", // existing destination
  "message": "[bif] queued The Bear /path/x.bif",
}
```

Timestamp rule already used in the codebase is honored: format `MM-DD HH:mm` is the
console style, but the **store** uses `yyyy/mm/dd hh:mm:ss`; hour `24` is normalized
to `00` (existing repo convention).

## 6. Rollout (phased — keep changes small and per-server deployable)

1. **Infra (no call-site edits):**
   - Create `logs/` dir + SQLite schema bootstrap.
   - Add common writer + `logEvent()` to `@tv/share`.
   - Add `POST /api/log` to srvr.
   - Add client `log.js` routine.
   - Deploy & smoke-test with a handful of manual events end-to-end.

2. **Codemod to instrument call sites (per project, one at a time):**
   - AST-based transform (e.g. jscodeshift / Babel for `.js`/`.vue <script>`) that:
     - finds `console.*` / `logSubtitle` / `log` / `loge` call sites,
     - allocates the next `log_id` (`SELECT max(log_id)+1`), derives `tag` from any
       `[tag]` prefix, maps the method to `level`
       (`warn`→warn, `error`→error, else info),
     - rewrites the call to go through the shared routine (preserving the original
       behavior), appends `// log-id: N`, and upserts the row into `log_sites`
       (descriptions only for the busiest sites; the log-agent fills the rest).
   - Process files bottom-up (or recompute line numbers post-edit) so inserted lines
     don't corrupt recorded `src_line` values.
   - Order by server so each can be deployed independently: `srvr` → `api` →
     `down` → `asr` → `tv` → `client`. (`./srvr <name>` per the repo workflow.)
   - Human pass to refine auto-generated descriptions where weak.

3. **Verify** after each server: `pm2 logs` shows no crash/restart loop; old log
   files still receive their lines; `all-logging.sqlite` receives rows.

## 7. Scope decisions

- **Included:** client, srvr, api, down, asr, tv, packages/share.
- **Excluded — android** (`apps/android/**`): android must not send logging messages.
- **Excluded — gitignored files:** build output, `temp*`, `node_modules`, etc.
- **Excluded — `scripts/`, `apps/*/scripts/`, and root files** (`*.cjs`,
  `scan-playback-positions.js`, etc.): confirmed out of scope (ad-hoc, not
  long-running, no pm2 capture).
- **Excluded — Tampermonkey `*.user.js`:** confirmed (foreign browser contexts).

## 8. Message length & long-line cleanup (precondition)

Per direction: **do not cap message size in the DB.** Instead, shorten over-long
_existing_ messages by editing the source first, and **don't enable universal logging
until the long-line cleanup is decided.**

- A one-time scan of the live logs is in `temp2.md`: every log statement that emits
  lines >120 chars, grouped by source location, sorted longest-first, with the actual
  longest example and occurrence counts.
- The biggest offenders are a handful of locations (the tvdb `enqueue … from: <stack>`
  dump, `tvdb push … <field diff>`, the down `------ … SKIPPING …` and `not blocked`
  progress lines, and chokidar `sub check … files=<all paths>`). Fixing ~5 locations
  removes most long-line volume.
- You decide which to shorten; the instrumentation step (§6) starts only after that.

## 10. Suggestions

- **Provide a tiny query helper** (`scripts/logq.sh "SELECT …"`) for one-line store
  scans during debugging. (Adopted.)
- **Stamp `pid` and `ts` in the collector**, not the caller, so cross-process ordering
  stays consistent.
- **Add an FTS5 index on `message`** later if the log pane needs fast text search.
- **Centralize `level` derivation** (one helper maps `console.warn`→warn,
  `console.error`→error, `logSubtitle`/`log`→info) so the codemod stays mechanical.
- **Defer old-file removal** until each server's events are confirmed in the DB, then
  strip the legacy writes per project.
